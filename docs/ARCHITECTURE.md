# Архитектура tuff (черновик v0)

Цель: **тот же Minecraft Java 26.3, только быстрее.** Протокол, формат мира и игровое поведение
совпадают с ванилью. Ванильный клиент подключается к нашему серверу, мир открывается в обе стороны.

Все ссылки на ванильный код ниже — это места для чтения в `reference/26.3/{server,client}-src/`.
Код оттуда не копируем (см. README, clean-room).

---

## 0. Принципы

1. **Два класса изменений.**
   - **[A] Поведение не меняется.** Другие структуры данных, кеши, отсутствие аллокаций, работа вне
     главного потока. Делаем свободно, но подтверждаем тестами на паритет (раздел 5).
   - **[B] Поведение меняется** (порядок обновлений, расход RNG, задержка на тик). Только под
     флагом в конфиге, **по умолчанию выключено**.
2. **Ориентир — не голая ванилла, а ванилла + Sodium / Lithium / C2ME.** Если мы не быстрее
   их, переписывание теряет смысл.
3. **Сначала замер, потом оптимизация.** Профилируем ванилу через `/jfr start` / `/jfr stop` на
   фиксированных сценариях и чиним то, что реально тормозит.
4. **Однопоточный тик не трогаем по смыслу, а делаем очень быстрым.** Всё, что не тик, выносим
   с главного потока.

## 1. Что Mojang уже исправила к 26.x (не изобретаем заново)

Проверено по коду 26.3. Многие старые претензии к Minecraft в этой версии уже неактуальны.

| Подсистема | Что сейчас в ванили | Где смотреть |
|---|---|---|
| Генерация мира | Функции плотности считаются **пачками по объёмам**: `DensityVolume`, float-буферы `DensityBuffer`, пулы буферов, правила переписывания графа `DfRewriteRule`, компилятор кешей | `world/level/levelgen/densityfunction/` |
| Рендер | Новый слой **renderpearl**: бэкенды Vulkan (на Mac через MoltenVK) и OpenGL, `drawIndexedIndirect`, общий `UberGpuBuffer` для мешей чанков | `com/mojang/renderpearl/`, `client/renderer/chunk/` |
| Окно и ввод | SDL вместо GLFW | `com/mojang/blaze3d/platform/` |
| Свет | BFS на очередях `LongArrayFIFOQueue` с упакованными в `long` записями, отдельный `ThreadedLevelLightEngine` | `world/level/lighting/`, `server/level/ThreadedLevelLightEngine.java` |
| Хранение блоков | Палитры: single / linear / hashmap / global + упакованные биты | `world/level/chunk/PalettedContainer.java` |
| Сжатие регионов | Кроме gzip/deflate есть `lz4` и `none` | `world/level/chunk/storage/RegionFileVersion.java` |
| Отправка чанков | Пачки с подтверждением от клиента, адаптивная скорость | `server/network/PlayerChunkSender.java` |
| Редстоун | Новый вычислитель провода под фичафлагом `redstone_experiments` | `world/level/redstone/ExperimentalRedstoneWireEvaluator.java` |

Вывод: **в генерации мира и рендере выигрыш будет умеренным.** Главные резервы — тик сервера,
сущности, память, сеть и сохранение.

## 2. Слабые места и что делаем мы

### 2.1 Весь сервер в одном потоке, измерения по очереди
- **Ваниль:** `MinecraftServer.tickChildren` обходит `getAllLevels()` и вызывает `level.tick()`
  по одному. Верхний мир, Незер и Энд ждут друг друга, хотя почти не связаны.
- **Мы:** у каждого измерения свой поток тика. Межмировые действия (переход через портал, глобальные
  команды, scoreboard, список игроков) складываем в очередь и применяем на **барьере в конце тика**.
- **Риск [B]:** сущность, прошедшая через портал, в ванили может тикнуть в новом мире в том же тике,
  а у нас — на тик позже. Нужен тест на порталах. Если расхождение заметно, делаем барьер сразу
  после фазы сущностей того мира, откуда она ушла.

### 2.2 Внутри измерения тоже один поток
- **Ваниль:** `ServerLevel.tick` выполняет фазы строго по очереди: погода → `blockTicks`/`fluidTicks`
  (до 65536 за тик) → рейды → чанки (случайные тики, спавн) → `blockEvents` → сущности → блок-сущности.
  Сущность N видит изменения, сделанные сущностью N−1 в этом же тике.
- **Почему нельзя просто распараллелить:** на этом порядке держатся фермы, дюпы и редстоун. Кроме того,
  `Level.random` — общий генератор случайных чисел. Параллельные регионы тратили бы его в другом
  порядке. Folia так и потеряла часть ванильного поведения.
- **Мы:**
  - [A] Фазы и порядок оставляем как в ванили. Ускоряем за счёт раскладки данных и отсутствия
    аллокаций (разделы 2.3–2.7).
  - [B] Опциональный режим «регионы» в стиле Folia для серверов, которым важнее онлайн, чем
    побитовый паритет. По умолчанию выключен.

### 2.3 Сущности — тяжёлые объекты с глубоким наследованием
- **Ваниль:** `Entity` (4331 строка) → `LivingEntity` (4158) → `Mob` (1487) → конкретный моб. Каждая
  сущность несёт все поля всех уровней, вызовы виртуальные, данные разбросаны по куче.
  Порядок тика задаёт `EntityTickList` (`Int2ObjectLinkedOpenHashMap`, порядок вставки).
- **Мы [A]:** хранение в стиле ECS: компоненты лежат плотными массивами (позиция, скорость, AABB,
  здоровье, AI отдельно). Пустые для этого вида компоненты не храним вообще.
- **Важно:** тикаем **не по архетипам, а по отдельному списку порядка**, совпадающему с ванильным.
  Ваниль внутри одной сущности перемежает движение, AI и коллизии. Разбить это на проходы
  «сначала все двигаются, потом все думают» нельзя, поведение поменяется. ECS здесь даёт
  локальность кеша и экономию памяти, а не параллельные системы.

### 2.4 Запросы «все сущности в AABB» на каждом шагу
- **Ваниль:** `level.getEntitiesOfClass(...)` вызывается постоянно и каждый раз создаёт новый `List`:
  - хоппер ищет предметы над собой (`HopperBlockEntity.getItemsAtAndAbove`);
  - предметы ищут, с кем слиться (`ItemEntity.mergeWithNeighbours`);
  - сенсоры мобов ищут соседей (`NearestLivingEntitySensor`);
  - коллизии собирают сущности (`Entity.collide` → `getEntityCollisions`).

  Индекс: секции 16³ в `Long2ObjectMap` + `LongAVLTreeSet` (`EntitySectionStorage`).
- **Мы [A]:**
  - Пространственный индекс по секциям с **корзинами по типу** (предметы, живые, вагонетки,
    прочие). Хопперу не нужно перебирать мобов.
  - Запросы без аллокаций: итератор или колбэк по срезам.
  - **Порядок результатов как в ванили** (порядок секций, внутри — порядок вставки). Хоппер берёт
    первый предмет, от порядка зависит поведение.

### 2.5 Коллизии
- **Ваниль:** каждое движение собирает `List<VoxelShape>` из блоков и сущностей и пересекает формы
  общим механизмом (`world/phys/shapes/`: `IndexMerger`, `DiscreteCubeMerger` …).
- **Мы [A]:**
  - Для каждой секции держим битовую маску «полный куб / пусто». Это подавляющее большинство
    блоков, их проверяем битовыми операциями.
  - Настоящие формы считаем только для неполных блоков (ступеньки, заборы и т.п.).
  - Ноль аллокаций.
  - Результат обязан совпадать с ванильным, включая эпсилоны и порядок осей.

### 2.6 Хопперы и блок-сущности
- **Ваниль:** каждый хоппер тикает каждый тик (перезарядка 8). Он ищет контейнер выше и ниже
  через `getBlockEntity`, а если там пусто — ещё и через AABB-запрос вагонеток с сундуком.
- **Мы [A]:**
  - Кешируем ссылки на соседние контейнеры и сбрасываем кеш при изменении блока.
  - Хоппер «засыпает», когда ему гарантированно нечего делать: источник пуст, предметов сверху
    нет, цель полна. Будим его ровно по тем событиям, которые в ванили изменили бы результат.
  - Паритет проверяем тестами на классических сортировщиках и фермах.

### 2.7 Обновления соседей и редстоун
- **Ваниль:** `CollectingNeighborUpdater` — стек на `ArrayDeque` с лимитом цепочки
  `maxChainedNeighborUpdates`. Провод по умолчанию — `DefaultRedstoneWireEvaluator`, известный
  лавиной лишних обновлений. Экспериментальный вычислитель — под флагом.
- **Мы:**
  - [A] Реализуем **оба** вычислителя бит-в-бит.
  - [A] Ускоряем только представление: очередь без аллокаций, предвычисленные таблицы соседей
    для состояний блоков.
  - **Порядок обновлений не меняем никогда.** На нём держится весь технический редстоун.

### 2.8 Состояние блока — объект с картой свойств
- **Ваниль:** `BlockState` — объект (`StateHolder`) с массивом свойств. `getValue` и `setValue`
  ищут свойство и переходят к соседнему состоянию через таблицы.
- **Мы [A]:** состояние блока — это число `u32`, глобальный id. Свойства — битовые поля внутри id,
  таблицы смещений генерируются при сборке. Все флаги («твёрдый», «прозрачный», «пропускает свет»,
  «полный куб», форма коллизии) лежат в плотных таблицах по id. Проверка флага — одно чтение
  из массива.

### 2.9 Чанки, тикеты и цепочки future
- **Ваниль:** `DistanceManager` + `ChunkHolder` + `ChunkMap` (1455 строк) + цепочки
  `CompletableFuture` на каждый этап генерации и `ChunkTaskDispatcher`. Сложно отлаживать,
  много мелких аллокаций.
- **Мы [A]:** явная машина состояний чанка (`Empty → Structures → Noise → Surface → Carvers →
  Features → Light → Full`) и **граф задач** с зависимостями от соседей (для фич нужны соседи
  в радиусе 1). Пул потоков с work-stealing. Уровни тикетов считаем так же, как ваниль
  (это влияет на то, какие чанки тикают).

### 2.10 Генерация мира
- **Ваниль:** уже пакетная (раздел 1), но это Java: стабильного SIMD нет (Vector API всё ещё
  incubator), граф функций — объекты с виртуальными вызовами.
- **Мы [A]:**
  - Граф функций плотности компилируем в плоский список инструкций над буферами.
  - Каждая инструкция — SIMD-цикл по объёму.
  - **Бит-в-бит с ванилью:** то же float/double, тот же порядок операций, без FMA. Шумы
    (improved Perlin, симплекс, `Xoroshiro128++`, легаси-LCG) реализуем точь-в-точь.
  - Ожидание: x1.5–3 к ванили, не больше. Это не главный резерв.

### 2.11 Сохранение и загрузка мира
- **Ваниль:** чанк превращается в дерево `CompoundTag` (хешмапы объектов), потом сжимается.
  При загрузке проходит через Codec и DataFixerUpper. Один `BlockStateData` — 9446 строк
  фиксов, `DataFixers` — 1713.
- **Мы [A]:**
  - Пишем и читаем NBT **потоково, прямо из структур чанка**, без промежуточного дерева.
  - Формат Anvil остаётся совместимым. Пишем `deflate` (по умолчанию) или `lz4` — ваниль читает оба.
  - **DataFixer не пишем.** Поддерживаем только формат 26.3. Старые миры сначала один раз
    открываются ванилью. Это экономит огромный кусок кода.
  - Сериализация в пуле потоков, запись на диск в отдельном IO-потоке.

### 2.12 Сеть
- **Ваниль:** Netty, объект на каждый пакет. `PlayerChunkSender.sendChunk` создаёт
  **новый** `ClientboundLevelChunkWithLightPacket` для каждого игрока, то есть один и тот же чанк
  сериализуется и сжимается заново для каждого. Сжатие zlib на каждый пакет отдельно
  (`CompressionEncoder`: `setInput → finish → reset`).
- **Мы [A]:**
  - Раз сжатие идёт пакет за пакетом, **готовые сжатые байты пакета чанка можно кешировать**
    (ключ: чанк + его версия + порог сжатия) и рассылать всем игрокам. Шифрование AES/CFB8
    остаётся своим у каждого соединения, но оно дешёвое.
  - Сжатие через libdeflate. Поток байт другой, но zlib валидный, клиенту всё равно.
  - Асинхронный ввод-вывод (tokio). Кодирование и сжатие идут в сетевых потоках, а не в потоке тика.
  - Протокол 26.3 генерируем кодом из описания пакетов, чтобы обновляться на новые версии.

### 2.13 Данные игры (реестры, рецепты, лут, генерация)
- **Проблема:** серверу нужны данные ванили: блоки, предметы, биомы, рецепты, таблицы лута,
  JSON генерации мира. Это ассеты Mojang, распространять их нельзя.
- **Мы:** **не храним и не распространяем их.** При первом запуске берём их из `server.jar`
  пользователя:
  - JSON из `data/` внутри jar;
  - отчёты встроенного генератора данных (`net.minecraft.data.Main --reports`) — списки блоков,
    состояний и id реестров.

  Протокол позволяет не пересылать реестры клиенту, если обе стороны знают пак `minecraft:core`
  (`KnownPack`).

### 2.14 Память
- **Ваниль:** у каждого объекта Java заголовок, коллекции объектов, мелкие временные объекты
  (`BlockPos`, `Vec3`, `AABB`) создаются миллионами. Большие кучи — длинные паузы GC.
- **Мы [A]:** значения на стеке (`BlockPos`, `Vec3`, `Aabb` — `Copy`-структуры), арены на тик,
  плотные массивы. GC нет, пауз нет.

### 2.15 Клиент (после сервера)
- **Ваниль:** рендер уже современный (раздел 1). Остаются:
  - паузы GC;
  - построение мешей на CPU через объектные модели блоков (`SectionCompiler`);
  - на Mac Vulkan через трансляцию MoltenVK.
- **Мы:**
  - wgpu: на Mac нативный Metal, без трансляции.
  - Компактный формат вершин.
  - Отсечение по фрустуму и окклюзии на GPU (compute) + indirect draw.
  - Меши строятся в пуле потоков из плотных таблиц моделей по id состояния.
  - Без greedy meshing: он ломает AO и текстуры, визуал должен совпадать.

## 5. Проверка паритета (без неё всё остальное не имеет смысла)

1. **Генерация:** один сид → ванильный сервер (из `server.jar` пользователя, headless) и наш →
   сравнение чанков блок в блок, плюс биомы и heightmap.
2. **Поведение:** сохранённый мир со схемой (редстоун, фермы, хопперы) + запись входящих пакетов →
   N тиков в ванили и у нас → дифф мира и сущностей.
3. **Формат:** мир, сохранённый у нас, открывается в ванили, и наоборот.
4. **Бенчмарки:** одни и те же сценарии для ванили, ванили с Lithium/C2ME и нас. Метрики:
   MSPT (p50/p99), RAM, скорость генерации чанков в секунду, трафик на игрока.

## 8. Тик: контракт и исполнение

Тик разделяем на **контракт** (что наблюдает игрок) и **исполнение** (как мы это считаем).
Контракт фиксируем и покрываем тестами паритета, исполнение переписываем как угодно.

### Три класса механик
1. **Зависят от точного порядка.** Редстоун, поршни, 0-тик, хопперы, дюпы TNT, ковров и рельс,
   квази-коннективность, update suppression. Порядок фаз, обновлений и сущностей не меняем никогда.
   Пример того, что бывает иначе, — Bedrock: тик устроен по-другому, схемы с Java там не работают.
2. **Статистические.** Случайные тики, рост, спавн, погода. Важно распределение, а не порядок.
   Здесь допустим генератор случайных чисел на каждый чанк, считаемый от (сид, тик, чанк).
   Тогда эти фазы можно считать параллельно, а выработка ферм не меняется. Ломается только
   RNG-манипуляция, поэтому это [B] под флагом, пока не докажем совпадение выработки.
3. **Невидимые внутренности.** Индексы, кеши, сон объектов. Полная свобода [A].

### Исполнение по шагам (каждый сверяется с шагом 1)
1. **Эталон:** простой однопоточный тик точно по ванилле.
2. **Сон и события [A]:** объект спит, пока не произойдёт событие, которое в ванилле изменило бы
   результат.
3. **Параллельная статистика [B]:** случайные тики и спавн по чанкам со своим RNG.
4. **Спекулятивный параллельный тик сущностей [A, исследование]:** сущности считаются параллельно
   в журналы, применяются в ванильном порядке, при конфликте чтения и записи сущность
   пересчитывается (идея Block-STM). Основание: в 26.3 сущности ~604 раза обращаются к своему RNG
   и ~22 раза к общему `level.random`, поэтому конфликты в основном пространственные.
   В плотных фермах выигрыша не будет.

## 9. Моды

| Что | Решение |
|---|---|
| Fabric / Forge / NeoForge на нашем сервере | **Не поддерживаем.** Mixin патчит байткод классов Mojang, которых у нас нет |
| Клиентские моды (Sodium, Iris, миникарты) | Работают сами: игрок заходит обычным клиентом с модами |
| Датапаки | Полная поддержка. `mc-data` и так читает ванильный контент в этом формате |
| Плагины Bukkit/Paper | Мост через встроенную JVM, по желанию, поздно (ROADMAP Ф9) |
| **Свой API (главное)** | Модель Hytale: моды только на сервере, игрок ничего не ставит |

### Свой API
- **Серверные моды на WASM:** песочница, любой язык, горячая перезагрузка, лимит времени на тик.
  Мод не может уронить сервер.
- **Контент описывается данными.** Движок сам собирает ресурспак и отправляет его при входе.
  - предметы — через компонент `item_model`;
  - блоки — через запасные ванильные состояния (нотный блок, грибные блоки, растяжка), коллизия
    от блока-донора;
  - мобы — на display-сущностях;
  - интерфейс — сундучные меню и встроенные диалоги.
- **В API с самого начала три части:** серверная логика / клиентский модуль / запасной вариант
  для обычного клиента. Клиентские модули заработают с нашим клиентом (ROADMAP Ф11). Тогда сервер
  присылает клиенту WASM, модели и анимации, есть API рендера с инстансингом. Это и нужно
  модам вроде Create.
- **Каталог хуков проектируем по данным:** рейтинг целей Mixin'ов в топ-модах Modrinth (ROADMAP Ф0).

### AI-перенос модов (ROADMAP Ф12)
Конвейер: разбор → классификация → перевод → WASM → тесты против оригинала на Fabric (тот же стенд
паритета) → отчёт о покрытии → ревью. Обязательно проверяются лицензия (All Rights Reserved — только
с разрешения автора) и похожесть на ваниллу (clean-room). Большие моды с клиентской частью
(Create) переносимы только на наш клиент с клиентскими модулями.

## 10. Целевая архитектура (версия 2026-10, к ней движемся по шагам)

### 10.1 Что есть сейчас (замер 2026-10-29)

- В `mc-server` 135 тыс. строк из 203 тыс. В нём живёт игровая логика (около 110 модулей:
  хопперы, варка, боссы, мобы, жители, карты), а доменные крейты тонкие.
- `ServerContext` — одно измерение, но это объект-свалка: 35 полей, 31 из них под своим
  `Mutex`; в `Shared` ещё около 30 замков. Около 450 захватов замков в `mc-server`, от
  `ServerContext` зависят 165 файлов. Отсюда риск взаимной блокировки (порядок замков нигде не
  записан), спор за замки между сетью и тиком и невозможность параллельных измерений.
- Сеть уже ходит в тик сообщениями (`tick::Request` → `Outcome`), но рядом читает и пишет
  состояние мира напрямую через замки.
- `unsafe` нет. Так и остаётся: `unsafe` допустим, только если бенчмарк доказал выигрыш, и
  тогда он изолирован в одном модуле с объяснением инвариантов.

### 10.2 Крейты и кто чем владеет

```
mc-nbt, mc-protocol, mc-data   форматы и данные; ничего не знают об игре
mc-world        чанки, секции, палитры, heightmap, хранимый свет; снимки секций (Arc, copy-on-write)
mc-light        расчёт света над mc-world
mc-worldgen     шум, биомы, поверхность          ┐ чистые функции:
mc-features     фичи и структуры, оверлей датапаков┘ (сид, координаты, данные) → блоки
mc-tick         фазы тика, запланированные тики, block events, соседи, редстоун, поршни, жидкости,
                логика блоков и блок-сущностей (хопперы, печи, варка, костры, крафтер, ...)
mc-entity       сущности, физика, пути, AI мобов, жители, рейды, боссы
mc-storage      регионы Anvil, (де)сериализация чанков, сущностей, игроков, level.dat, апгрейд старых миров
mc-command      дерево команд, разбор аргументов и селекторов
mc-level        (новый) состояние одного измерения `Level` и сборка систем в тик: владеет миром,
                сущностями, активными блок-сущностями, тикетами, погодой, POI; вызывает mc-tick и
                mc-entity в ванильном порядке фаз. Сюда переезжает склейка, которая сейчас в
                tick.rs/world.rs.
mc-server       только: сеть и состояния соединения, сессии игроков, перевод пакетов в запросы к
                тику и ответов в пакеты, консоль, RCON, query, management API, бэкапы, уведомления,
                конфиг, запуск и остановка. Никакой игровой механики.
```

Правило направления: зависимости идут только вниз по списку. Доменный крейт не знает о сети и
о `mc-server`. Если системе нужно что-то из соседнего домена (хоппер всасывает сущность-предмет),
она получает узкий интерфейс (трейт или срез данных) от `mc-level`, а не весь контекст.

Пока `mc-level` не выделен, системы переезжают из `mc-server` в доменные крейты по одной: логика
(«что происходит») уходит вниз, а в `mc-server` остаётся тонкая обёртка, которую потом заберёт
`mc-level`. Новых механик в `mc-server` не добавляем.

### 10.3 Владение состоянием и тик

- **Измерение принадлежит своему потоку тика.** `Level` передаётся системам как `&mut Level`,
  без замков. Поля, которые сейчас под `Mutex` в `ServerContext`, становятся обычными полями.
- **Общее состояние сервера делится на три вида:**
  1. неизменное после старта: данные, реестры, теги, конфиг, команды (`Arc`, без замков);
     `/reload` подменяет снимок целиком (`util::Publish`, то есть атомарная замена `Arc`);
  2. глобальное игровое состояние: время, правила игры, scoreboard, хранилище команд,
     боссбары, карты, статистика. Меняется только координатором тика в фазе «сервер» до и после
     измерений; измерения в своей фазе видят его только на чтение и пишут в почтовый ящик;
  3. настоящие общие службы, которые трогают и сеть, и тик: список игроков онлайн, whitelist и
     баны, файлы игроков, шина management API. Каждая — один замок или атомарный снимок, замки
     никогда не вкладываются друг в друга, держатся только на время копирования.
- **Порядок тика сервера** (как в ванили `MinecraftServer.tickServer`): входящие задачи сети →
  фаза «сервер» (время, правила, планировщик функций) → измерения по очереди: верхний мир, Незер,
  Край → переносы между измерениями (порталы, телепорты) → сеть получает результаты →
  автосохранение планируется. Пока измерения идут по очереди, поведение совпадает с ванилью.
- **Параллельные измерения** — вариант того же цикла: фаза измерений идёт в трёх потоках, каждый со
  своим `&mut Level`, общий вид — только чтение, межизмеренческие эффекты пишутся в ящики и
  применяются после барьера в порядке индексов измерений. В ванили сущность из портала попадает в
  Незер в тот же тик, если верхний мир тикается раньше; при барьере — так же, если перенос
  применяется до тика Незера следующего шага. Каждое расхождение, которое видно игроку, — повод
  держать режим под флагом [B]; решение принимается по тестам паритета на порталах.

### 10.4 Сеть и тик

```
поток соединения (tokio)  декод → проверка лимитов → Request в ящик измерения игрока
поток тика                в начале тика разбирает ящик (как ванильный runAllTasks), выполняет,
                          складывает ответы игроку (Outcome) и события для всех (Event)
поток соединения          получает Outcome/Event, кодирует, сжимает, шифрует, отправляет
```

- Сеть **не читает мир под замком**. Ей нужны: снимок чанка для отправки (тик отдаёт `Arc` на
  неизменяемые секции, кодирование и сжатие делает поток соединения или пул), позиции и данные
  сущностей для трекинга (готовые пакеты от тика), ответы на запросы. Всё приходит сообщением.
- Лимиты против злонамеренного клиента стоят на границе: размер кадра и распаковки, глубина и
  размер NBT, длина строк и списков, число пакетов в секунду, работа на пакет. Тик получает только
  уже проверенные запросы.

### 10.5 Что не на потоке тика

Генерация и свет чанков (пул), кодирование и сжатие чанков, сериализация и запись чанков при
автосохранении (тик отдаёт снимки секций, дальше работает IO-поток), запись файлов игроков и
статистики, `/pregen`, бэкапы, запросы к Mojang, management API, RCON, query. Ничего из этого не
берёт замок, который берёт тик, кроме служб вида 3, и то на время копирования.

### 10.6 Точки расширения для Ф8 и пакетов с сервера

- **Моды WASM (Ф8)** работают на потоке тика своего измерения, в определённых фазах (до и после
  фаз ванили, события блоков, сущностей, команд), с доступом к `Level` через узкий API хоста
  (прочитать и поставить блок, найти сущности, послать пакет игроку). Поэтому системы должны
  вызываться как функции над `&mut Level`, а события тика — быть явными значениями, а не побочными
  эффектами внутри замков. Лимит времени на тик для мода — счётчик топлива WASM.
- **Пакеты, которые сервер присылает при входе** (CONCEPT.md): у мира есть список пакетов с
  версиями и хэшами; фаза конфигурации соединения отдаёт его клиенту наряду с датапаками и
  ресурспаком. Нужна одна точка в `mc-server` — список «что прислать при входе», который
  собирается из датапаков, ресурспака и пакетов, а не три разных механизма.
- Реестр контента (блоки, предметы, сущности от пакетов) расширяет `mc-data` при загрузке; игра
  обращается к контенту по id, поэтому моды не требуют правки систем.

### 10.7 Правила для каждого изменения

- Новая механика пишется в доменном крейте, не в `mc-server`.
- Новое поле в `ServerContext` или `Shared` — только с записанной причиной; новый замок на пути
  тика — нельзя.
- Файл больше ~1500 строк делится по настоящим швам (по подсистеме, а не «part1/part2»).
- Перед слиянием ветку читает отдельный ревьюер архитектуры по этим правилам.
