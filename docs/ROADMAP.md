# План работ minecraft-rewrite

Архитектура и обоснования — в [ARCHITECTURE.md](ARCHITECTURE.md). Здесь только **что, в каком порядке
и когда фаза считается готовой**.

**Сроки — грубая оценка** для одного человека на полной занятости с AI-агентами. Могут ошибаться
в два раза в любую сторону. Главное здесь порядок, а не даты.

---

## Общая логика порядка

1. **Сначала сервер, потом клиент.** Сервер проверяется обычным клиентом с первого дня, на нём самый
   большой и измеримый выигрыш, и клиентские моды игроков продолжают работать.
2. **Сначала эталон, потом скорость.** Каждая подсистема сначала пишется простой и точной копией
   поведения ваниллы, покрывается тестами паритета и только потом ускоряется. Тест паритета —
   приёмочный критерий каждой задачи.
3. **Архитектуру под быстрое закладываем сразу**: плотные данные, без аллокаций в горячих местах,
   задачи вне потока тика. Рискованные оптимизации (порядок, RNG, параллельный тик) — только после
   эталона.
4. **Моды — после того, как сервер играбелен.** API модов не стабилизировать, пока движок меняется.

```
Ф0 Фундамент ─► Ф1 Протокол ─► Ф2 Мир/хранение ─► Ф3 Тик-эталон ─► Ф5 Сущности ─► Ф6 Команды/датапаки
                                     │                                                    │
                                     └──► Ф4 Генерация мира (параллельный трек) ──────────┤
                                                                                          ▼
                    Ф7 Оптимизации ◄── (после каждой фазы точечно, по-крупному здесь) ── M6 «можно заменить ванильный сервер»
                                                                                          │
                              Ф8 API модов (сервер, WASM) ─► Ф9 Мост Bukkit (по желанию)  │
                                                                                          ▼
                              Ф10 Свой клиент ─► Ф11 Клиентские модули ─► Ф12 AI-перенос модов (Create и др.)
```

## Процесс, который действует во всех фазах

### Всё как в ванили, до мелочей

Мы **переписываем** ванильный сервер, а не изобретаем свой. Всё, что видит игрок или
администратор, должно быть как в ванили: сообщения чата, ошибки команд и их подсказки
(автодополнение), уведомления, тексты отключения и кика, вывод консоли, файлы сервера
(`server.properties`, `ops.json`, `whitelist.json`, `banned-*.json`, `usercache.json`,
`logs/`, папка мира), значения по умолчанию. Тексты — теми же ключами перевода с теми же
аргументами, чтобы клиент показывал их на языке игрока. Нашли отличие — это баг.

### Clean-room с AI-агентами (две роли)
Агент, который читает `reference/`, и агент, который пишет код, — **разные сессии**.
- **Читатель** изучает декомпилированный код и пишет спецификацию поведения своими словами в
  `docs/specs/<подсистема>.md`. Только описание: что происходит, в каком порядке, крайние случаи.
  Без кода и без копирования идентификаторов, кроме имён из протокола и формата данных.
- **Писатель** реализует по спецификации и **не имеет доступа к `reference/`**.
- В CI проверка на похожесть: наш код сравнивается с декомпилированной ваниллой по совпадающим
  фрагментам и при совпадении отклоняется.

### Тесты паритета — приёмка
Ванильный `server.jar` пользователя запускается без интерфейса рядом с нашим, на одном мире, с одними
действиями. Состояние после N тиков сравнивается. Каждая задача закрывается, только когда её
сценарии проходят.

### Новые версии Minecraft
Для каждой версии храним декомпилированный код в `reference/<версия>/`. **Дифф между версиями** —
точный список изменений. Из него делаем задачи: протокол, данные, поведение.

### Как работать с агентами
- Каждая фаза начинается в plan mode, разбиваем её на задачи с тестами.
- Одна задача — одна сессия, одна подсистема, свой набор файлов, чтобы агенты не писали в одни
  и те же файлы.
- Приёмка задачи — тест паритета или бенчмарк, а не «вроде работает».

## Ф0. Фундамент — 2–4 недели

**Цель:** всё готово, чтобы писать код с тестами и замерять.

- Имя и email в git, первый коммит, лицензия **нашего** кода (решение за тобой: MIT/Apache-2.0
  или GPL/AGPL).
- Cargo workspace с пустыми крейтами из ARCHITECTURE.md §3, CI: `fmt`, `clippy`, тесты.
- Проверки clean-room в CI: ничего из `reference/` и `tools/` в git, проверка на похожесть.
- Извлечение данных из `server.jar` пользователя: встроенный генератор (`--reports`) + JSON из
  `data/` → в кеш, который потом читает `mc-data`.

## Ф1. Протокол и вход — 1–2 месяца → **M1: ванильный клиент заходит**

- `mc-nbt`: потоковое чтение и запись + дерево для тестов.
- `mc-protocol`: VarInt, фреймы, сжатие, шифрование AES/CFB8, пакеты генерируются кодом из описания.
- Состояния протокола: handshake → status (MOTD в списке серверов) → login (сначала offline,
  потом online с проверкой сессии Mojang) → configuration (реестры через `KnownPack`, теги) → play.
- Play-минимум: вход в мир, плоские или пустые чанки, keepalive, движение, чат, выход.
- Бот-клиент для нагрузочных тестов.

**Готово, когда:** клиент 26.3 видит сервер в списке, заходит в online-режиме, ходит, пишет
в чат, 100 ботов держатся без ошибок.

**Риск:** протокол большой. Кодоген окупится с первого же обновления версии.

**Статус (2026-10-17), первый срез:**

## Ф2. Мир и хранение — 1–2 месяца → **M2: открываем существующий мир**

  хранение света (пока читаем готовый).
- `mc-storage`: регионы Anvil, чтение и запись, deflate/lz4, потоковый NBT, IO-поток.
- Система загрузки чанков: тикеты, дистанции, граф задач в пуле потоков.
- Отправка чанков с **кешем сжатых пакетов**.

**Готово, когда:** мир, созданный в ванилле, открывается и прогуливается. После изменений и
сохранения он **побайтно по смыслу совпадает** при открытии в ванилле, и наоборот. Скорость
загрузки чанков сравнена с ваниллой.

## Ф3. Тик-эталон: блоки и редстоун — 2–3 месяца → **M3: редстоун бит-в-бит**

- Скелет фаз тика строго в ванильном порядке (ARCHITECTURE.md §2.2, §8).
- Утилиты совместимости с Java: `java.util.Random`, генераторы MC (`Xoroshiro128++`, LCG),
  целочисленная арифметика как в Java, **копия порядка обхода `HashMap`/`HashSet` из Java**
  и `hashCode` нужных типов, таблицы `Mth`.
- Запланированные тики блоков и жидкостей с приоритетами, случайные тики, block events, обновления
  соседей с лимитом цепочки.
- Блоки: провод (оба вычислителя), повторитель, компаратор, факел, наблюдатель, поршни, нотный блок,

## Ф7. Оптимизации — 2–4 месяца, потом постоянно

Очень важно (решение владельца): пройтись по всему, что сильнее всего нагружает сервер, и
ускорить по максимуму с минимальными отличиями от ванили. В первую очередь:
- взрывы (1000 TNT разом не должны класть сервер);
- загрузка и генерация чанков (быстрая прогрузка: параллельная генерация, кэш, сжатие);
- свет, жидкости, редстоун, сущности, сохранение мира (автосохранение не на потоке тика).

Только поверх зелёных тестов паритета, каждая с бенчмарком «до/после».
- Сон хопперов и сущностей на событиях.
- Параллельные измерения с барьером (проверить порталы).
- Генератор случайных чисел на каждый чанк для случайных тиков и спавна (флаг [B]).
- Исследование: спекулятивный параллельный тик сущностей с перепроверкой (ARCHITECTURE.md §8).
- **Встроенная предгенерация чанков** (решение владельца), как плагин Chunky: `/pregen`. Это
  своя команда сверх ванили (ванильные не меняет), поэтому исключение из «всё как в ванили».
  - `/pregen start <центр x z> <радиус в блоках> [квадрат|круг] [измерение]`, а также `pause`,
    `continue`, `cancel`, `status`. По праву `pregen.*` (без настройки — операторы) и из консоли.
  - Генерирует в фоне, ближние чанки первыми, на ограниченном числе потоков, чтобы MSPT
    игроков не проседал. Сразу сохраняет на диск и выгружает, так что память не растёт с
    размером области.
  - Прогресс (готово/всего, чанков в секунду, сколько осталось) в консоли и у запустившего.
    Задача переживает перезапуск сервера и продолжается с места остановки.
  - **Готово, когда:** область радиусом 5000 блоков генерируется без роста памяти, а мир
    после неё открывается ванильным сервером 26.3 без ошибок и перегенерации.

**Готово, когда:** на сценариях Ф0 мы быстрее ваниллы с Lithium/C2ME по MSPT (p50 и p99) и RAM.

## Ф8. Серверный API модов (WASM) — 2–3 месяца

- Каталог хуков по рейтингу из Ф0, описания контента данными.
- Автосборка ресурспака и отправка при входе, раскладка кастомных блоков по запасным состояниям,
  модели мобов на display-сущностях, диалоги.
- Песочница, лимит времени на тик, горячая перезагрузка, SDK, документация.
- **Разделение в API сразу:** серверная логика / клиентский модуль (на будущее) / запасной вариант
  для обычного клиента.
- **Единый формат пакета** (решение владельца: моды и датапаки не разделять). Пакет — это
  датапак с расширениями, каждая часть необязательна: данные (как ванильный датапак), ассеты (как
  ресурспак), серверный WASM, клиентский WASM (Ф11). Простой мод — просто датапак. Манифест с
  зависимостями, точными версиями и хэшами.
- **Пакеты привязаны к миру, а не к клиенту:** список лежит в мире, как датапаки сейчас; у
  одиночной игры тот же механизм (наш сервер внутри клиента). Установленных в клиент модов нет.
- Что API даёт модам: события, планировщик задач, регистрация команд (с автодополнением у
  клиента), свои узлы прав из системы прав Ф6, дополнительные миры и измерения, хранение
  настроек и данных мода.

**Готово, когда:** три примера модов (контент, твик геймплея, мини-игра) работают на обычном клиенте
без установки чего-либо.

## Ф9. Мост для Bukkit/Paper — по желанию, 3+ месяцев

Встроенная JVM + реализация интерфейсов Bukkit/Paper API поверх движка. События на потоке тика.

**Готово, когда:** LuckPerms, Vault и несколько популярных плагинов без NMS работают.

## Ф10. Свой клиент — 6–12 месяцев

- wgpu (Metal на Mac), построение мешей в пуле потоков, отсечение на GPU + indirect draw.
- Ассеты из `client.jar` пользователя. Модели сущностей в ванилле заданы кодом, их нужно
  воспроизвести по спецификации (clean-room!).
- Все экраны интерфейса, звук, ввод, одиночная игра = наш сервер внутри клиента.
- **Контейнеры вместо общего главного меню** (решение владельца): первый экран — список
  контейнеров; у каждого свои пакеты, миры, серверы, настройки и главное меню; модпак с платформы
  ставится как контейнер; пакеты в общем кэше. Подробно — CONCEPT.md.
- **Нативная поддержка шейдеров** (решение владельца): отложенное освещение, тени, свой формат
  шейдер-паков, плюс совместимость с паками Iris/OptiFine (GLSL переводится для wgpu).
- **Пакеты с сервера:** при входе сервер присылает список пакетов с версиями и хэшами; клиент
  докачивает недостающее с платформы в общий кэш (один пакет хранится один раз), загружает на
  время сессии и выгружает при выходе. Игрок сам ставит только своё: шейдеры, ресурспаки,
  интерфейс.

**Готово, когда:** наш клиент играет и на нашем, и на ванильных серверах. FPS сравнен с ваниллой
и Sodium. Популярные шейдер-паки (BSL, Complementary) работают.

## Ф11. Клиентские модули — модель Hytale — 3–6 месяцев

- Сервер присылает клиенту WASM-модули, модели и анимации при входе.
- Песочница для клиентского WASM: без доступа к файлам и сети, только API клиента. Код с сервера
  не должен навредить игроку.
- **Клиентские пакеты** (ставит игрок в контейнер, живут, пока он открыт): главное меню, настройки, интерфейс,
  рендер, ввод. Права по манифесту, как у расширений браузера; сервер такие присылать не может.
- **Точки перехвата вместо Mixin:** именованные места движка (до, после, обернуть, заменить),
  заменяемые компоненты в реестре, интерфейс описан данными и правится патчами. Стабильный API и
  внутренний («может измениться»). Подробно — CONCEPT.md.
- Для разработчиков: привязки для языков, собираемых в WASM, горячая перезагрузка, режим
  разработчика (локально одной командой, список точек и кто их занял, отладчик, профайлер).
- API рендера с инстансингом (аналог Flywheel), свои экраны и оверлеи, физика игрока для
  движущихся конструкций.
- Плавное ухудшение для обычного клиента.

**Готово, когда:** пример мода с тысячами вращающихся деталей и движущейся платформой работает на
нашем клиенте, а на обычном показывает упрощённую версию.

## Ф12. AI-перенос модов — постоянно

- Конвейер: разбор → классификация → перевод → сборка в WASM → тесты против оригинала на Fabric
  → отчёт о покрытии → ревью человеком.
- Проверка лицензии, фильтр похожести на ваниллу.
- Порядок: маленькие контентные моды → библиотеки (прослойки Fabric API, GeckoLib) → Create
  (Flywheel, Ponder, Registrate прежде самого мода).

## Платформа — параллельный трек, после M6

Свой сервис (решение владельца), начинается с аккаунтов и растёт в каталог контента.
- **Аккаунты, ники и скины.** API совместимый с Yggdrasil (как ely.by и authlib-injector).
  Ник, существующий у лицензии Mojang, можно занять только после входа через Microsoft. Своим
  аккаунтам выдаются UUID из отдельного пространства, чтобы не совпадать с лицензионными. Если
  ник позже покупают в Mojang, лицензия побеждает. Скины хранятся в сервисе и подписываются его
  ключом, так что их нельзя подменить и они не ломаются.
- **Третий режим входа на нашем сервере:** «Mojang или платформа»; чужой ник не пройдёт ни
  там, ни там. Проверка только на сервере: клиентскую часть можно вырезать, это ничего не даёт.
- **Каталог:** пакеты (моды, датапаки, ресурспаки — единый формат Ф8), модпаки, шейдеры,
  плагины. Версии, зависимости, хэши, раздача через CDN, проверка WASM на вредоносное,
  модерация, страницы авторов, API для лаунчеров.

**Готово, когда:** на нашем сервере в режиме платформы нельзя зайти под чужим ником, скины видны
всем без плагинов, а клиент сам докачивает пакеты сервера из каталога.
