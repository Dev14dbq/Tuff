# Трек «Клиент»: каркас свой, части Horizon

Решение владельца (2026-10-29): клиент Tuff пишем со своей архитектурой, а у Horizon берём
отдельные части, где мало ванильной логики и много инженерии. Каждую взятую часть со временем
заменяем своей. Свой каркас нужен потому, что главная идея Tuff (сервер присылает пакеты,
клиент грузит их в песочнице, контейнеры из CONCEPT.md) должна быть в основе клиента, а не
прикручена сбоку.

Разбор сделан по `horizon-rust/horizon`, коммит `7c1e0f9` от 2026-10-29. Клон лежит только
локально в `external/horizon/` (папка в `.gitignore`). В git попадает только то, что мы
вырезали под свой клиент: в наш крейт, с пометкой источника и коммита.

## Что внутри Horizon

725 тыс. строк Rust в 31 крейте. Главное:

| Крейт | Строк | Что это |
|---|---|---|
| `horizon-client` | 333 тыс. | Сама игра: геймплей, сеть, экраны, встроенный и выделенный сервер |
| `horizon-world` | 168 тыс. | Данные мира и серверная логика блоков, генерация, datafix |
| `horizon-client-render` | 93 тыс. | Рендер, меши, свет, стриминг чанков, HUD, меню, звук. В геймплей не лезет |
| `horizon-core` | 20 тыс. | Java `Random`, `jmath`, позиции, шум, палитры |
| `horizon-protocol` | 12,5 тыс. | Протокол 777 |
| `horizon-assets` | 5,9 тыс. | Модели блоков и предметов, атласы. Зависит только от `horizon-core` |
| `horizon-client-input` | 4,3 тыс. | Клавиши, мышь, геймпад, окно |
| `horizon-shaders`, `horizon-shader-api` | 8,9 тыс. | Шейдер-паки (формат `shaders/`, у них написан clean-room) и свои WGSL-паки |
| `horizon-hdr`, `horizon-threads` | 0,6 тыс. | HDR, приоритеты потоков. Без зависимостей |

**Архитектуру их игры не берём ни в каком виде.** Вся игра держится на `struct Game`
примерно с 290 полями, методы которого разбросаны по ~180 файлам. Игроков сервера они
обрабатывают так: подменяют состояние гостя внутри `Game` на один вызов, а измерения
подменяют целиком. Это то, от чего мы сами уходим в `ServerContext`.

Ванильную логику они переносят по методам: таблица «метод ванили → файл Rust» (port
ledger). Поэтому каждая часть перед заимствованием проходит проверку похожести.

## Проверка похожести

`cargo xtask similarity --reference reference/26.3/client-src --ours external/horizon/crates`
(декомпилированный клиент 26.3 вместе со встроенным сервером), порог 12 общих отпечатков:

- **`horizon-client-render/src/mesher/lighting.rs` — 33 общих отпечатка с `BlockModelLighter`**
  (сглаженное освещение и ambient occlusion блоков), 12% файла. Это перенос ванили.
  **Не берём**, пишем сами по спецификации.
- Три файла `horizon-world/src/datafix/` ровно на пороге. Не берём (мир у нас свой).
- `horizon-client-input/src/key_names.rs` — 11, ниже порога; совпадают числовые таблицы кодов
  клавиш, не логика. Можно брать, но перепроверить глазами.
- Остальной рендер: один файл с 4, остальные 0–2. Чисто.

Проверка ловит близкие копии, но не доказывает clean-room: структуру, перенесённую с
ванили, она может не увидеть. Поэтому каждую взятую часть ещё читает агент-ревьюер.

## Что берём, что нет

**Берём** (после замены зависимостей и проверки):
- рендер-ядро `horizon-client-render`: `gfx` + `gfx.rs` (24 тыс.: рендерер, отсечение,
  окклюзия, прозрачность, загрузка на GPU, тайминги), `mesher` без `lighting.rs`,
  `streaming.rs` (пул потоков: генерация, свет, меши), `lod` (дальние чанки), `camera.rs`,
  `fog.rs`, облака, небо, погода;
- `horizon-assets` — модели и атласы из `client.jar` игрока;
- `horizon-client-input` — ввод и окно;
- `horizon-hdr`, `horizon-threads`, `horizon-shaders`, `horizon-shader-api`;
- их патч `wgpu-hal` (или ждём его в апстриме wgpu).

**Решаем позже, по одной:** частицы, рендер блок-сущностей, звук. Брать можно, но сначала
нужен свой каркас, чтобы было понятно, куда их встраивать.

**Пишем сами:** экраны, HUD, чат, меню настроек (у нас контейнеры вместо общего главного
меню, интерфейс должны менять пакеты), сглаженное освещение блоков.

**Не берём:** `horizon-client` (игра), `horizon-world` (у нас свой мир и сервер),
`horizon-protocol` (свой `mc-protocol`), `horizon-command`, `horizon-items`, серверные крейты,
телеметрию, Play with Friends. Их WASM-моды (`horizon-mods`, WIT) читаем как пример, но API
проектируем свой под пакеты с сервера.

## Что придётся развязать

Рендер ссылается на их мир и ядро:
- `horizon_world::nbt` (36 мест) и `horizon_world::registry` (22) → наши `mc-nbt` и `mc-data`;
- `horizon_core` в 43 файлах (позиции, палитры, текст) → наши типы;
- `horizon_client_core` в 12 файлах (текст, язык) → своё;
- `horizon_items`, `horizon_protocol`, `horizon_telemetry` — по 2–4 файла, убрать.

Версии: wgpu 30.0.1, naga 30.0.1, winit 0.30.13.

## Только Rust, без Java

Решение владельца (2026-10-29): у игрока и у админа на компьютере только наша программа. Ни
Java, ни Rust-тулчейна, ни ручного скачивания jar. Horizon так не умеет: их `horizon-prepare`
гоняет Java-экспортёры по установленной игре.

**Граница, которую нельзя переходить.** Текстуры, звуки, модели, шрифты, язык и ванильный
датапак принадлежат Mojang. Раздавать их со своего сервера или CDN — это распространение
чужого контента, за это закрывают проекты. Поэтому:
- **ванильные ассеты** клиент сам скачивает с официальных серверов Mojang
  (`piston-meta`/`piston-data`, `resources.download.minecraft.net`) после входа через
  Microsoft, как официальный лаунчер: проверяет SHA1, кладёт в общий кэш и читает из `client.jar` и
  объектов ассетов прямо в Rust;
- **с нашего сервера** приходит только наше и серверное: пакеты сервера (их модели, текстуры,
  звуки, WASM), ресурспак сервера, данные платформы.

**Сервер без Java.** Сейчас Java нужна только для `extract-data`: он запускает генератор
отчётов из `server.jar` (`reports/`: блоки и состояния, реестры, номера пакетов, команды,
18 МБ). Датапак ванили и `version.json` Rust уже читает из jar сам. План:
- сервер при первом запуске сам скачивает `server.jar` у Mojang (он публичный и бесплатный),
  проверяет SHA1 и читает из него `data/` и `version.json`;
- отчёты генерирует наш CI (с Java) для каждой версии Minecraft и кладёт в релиз Tuff
  в сжатом виде. Это таблицы чисел и имён для совместимости (номера блоков, пакетов,
  реестров), не контент; так же делают minecraft-data, Pumpkin и Minestom. Решено
  владельцем 2026-10-30: кладём.

**Готово, когда:** на чистой машине без Java и Rust скачанный бинарник Tuff (сервер или
клиент) сам готовит всё, что нужно, и запускается; ни в репозитории, ни в релизах нет
ассетов Mojang.

## Лаунчер для всех

Решение владельца (2026-10-30): Tuff доступен всем, лицензия для игры не нужна. Мы в СНГ, и
большинство игроков сидит на TLauncher и подобных, которые забиты рекламой и мусором. Наш
аргумент: то же самое, только чисто, с открытым кодом и быстрее.

- **Запуск без лицензии.** Никакой проверки покупки ни для запуска, ни для серверов Tuff.
- **Свои аккаунты платформы:** ники и скины (Yggdrasil, как ely.by), скины видны всем на
  серверах Tuff без плагинов.
- **Переезд в один клик.** Лаунчер находит папки TLauncher, Legacy Launcher, официального
  лаунчера, Prism, MultiMC, ATLauncher и забирает версии, миры, настройки, ресурспаки и
  скины. Клиент читает ассеты прямо из найденной установки. Есть «указать папку вручную»,
  флаги `--game-dir` и `--version` для запуска из чужих лаунчеров.
- **Вход Microsoft — бонус:** скин Mojang, online-серверы, скачивание игры с официальных
  серверов Mojang (только для аккаунта с покупкой).
- **Чистота:** ни рекламы, ни встроенных программ, ни телеметрии без согласия.

**Если Minecraft на диске нет**, клиент всё равно запускается — на запасном наборе ассетов
Tuff (свои текстуры с нуля под открытой лицензией, не перерисовка ванили) — и показывает
экран с тремя кнопками:
1. «У меня есть Minecraft — указать папку»;
2. «Войти через Microsoft» (с лицензией игра скачается с серверов Mojang);
3. «Поставить бесплатный пак» — пак Tuff или паки сообщества под открытой лицензией с нашей
   платформы.

**Чего клиент и лаунчер не делают никогда:** не скачивают файлы Mojang для аккаунта без
покупки, не ссылаются на сторонние сайты с ассетами Mojang, не раздают их с нашей платформы.
Одна такая функция — и Mojang сносит репозиторий целиком вместе с сервером.

## Фазы

### Ф0. Каркас клиента

Свой крейт `tuff-client`: окно, цикл кадра, подключение к серверу через `mc-protocol`, вход,
получение чанков. Одиночная игра — сервер Tuff внутри клиента. Место под пакеты с сервера и
WASM-песочницу заложено в архитектуре сразу (см. CONCEPT.md, ARCHITECTURE.md).

**Готово, когда:** клиент заходит на сервер Tuff и ванильный сервер 26.3 и получает мир (пока
без картинки).

### Ф1. Рендер из Horizon

Перенос рендер-ядра, `horizon-assets` и ввода в отдельные крейты Tuff с записью источника
(коммит Horizon) и их MIT-уведомлением в `THIRD_PARTY_NOTICES.md`. Зависимости заменены на
наши. Сглаженное освещение написано заново по спецификации.

**Готово, когда:** в клиенте Tuff виден мир с сервера, можно ходить, `cargo xtask similarity`
против клиента 26.3 чистый по всем крейтам клиента.

### Ф2. Игровой клиент

Свои экраны и HUD, инвентарь, чат, сущности, звук. Решение по частицам и блок-сущностям.

### Ф3. Пакеты с сервера

Сервер присылает список пакетов, клиент докачивает и грузит WASM в песочнице (Ф10–Ф11
ROADMAP).

### Дальше: замена взятого

Каждая часть Horizon помечена в коде. Заменяем её своей, когда до неё доходят руки или она
мешает нашей архитектуре. Цель — чтобы в `THIRD_PARTY_NOTICES.md` про Horizon осталась
только строка благодарности.
